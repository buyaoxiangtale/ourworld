## 15 分钟并发基线

500 条认证 WebSocket 连接、100 次/秒的混合业务请求持续 15 分钟；两个 API 实例。业务检查 90,496/90,496 成功，100 RPS 场景有 4 次迭代未能启动；全部 HTTP 请求（含登录与续期）失败率 0.41%，P95 7.24 ms，消息投递 P95 99 ms。该次运行的阈值通过（HTTP 失败率 <1%、P95 <500 ms、消息 P95 <1 s），并非零错误。监测样本中两个 API 合计维持 500 条连接超过 15 分钟。原始结果：`artifacts/load-summary.json`、`load-full.log`、`load-resources.json`、`load-benchmark-manifest.json`，当次脚本保存在 `artifacts/load-baseline-script.js`。

383 次 HTTP 失败均出现在令牌续期（401：262 次，429：121 次），业务请求检查全部成功。检查发现当次测试脚本按跨场景 VU 编号取模分配账号，可能使两个连接复用并轮换同一刷新凭据；失败重试也可能触发续期限流。这与观察到的状态码吻合，但属于原因推断。后续脚本改为场景内唯一编号并为各 HTTP VU 独立登录；续期专项结果另行记录，不能回填改写原基线。

续期专项使用更新后的脚本、最终 Docker 镜像，以 500 个不同账号建立连接，同时运行 100 RPS 六分钟：500 次 WebSocket 续期均收到重新认证确认，38,101 次 HTTP 请求零失败，HTTP P95 8.55 ms、消息投递 P95 99 ms；100 RPS 场景有 6 次迭代未能启动。专项结果见 `artifacts/load-renewal-summary.json` 和 `load-renewal.log`。此专项验证 WebSocket 续期；六分钟不足以覆盖脚本中九分钟后执行的 HTTP VU 自身续期。

本地压测期间临时将登录限流提高至每分钟 2000 次以准备 500 个测试账号；普通运行恢复默认值 60。结果反映这台机器和本地数据，不等于生产环境容量保证。

当前 Nginx 反代下，认证相关的按 IP 限流看到的是网关 IP，多个客户端会共用额度；已登录业务接口的用户维度限流不受此问题影响。公开部署前需要配置只信任受控网关的真实客户端地址、验证代理头不能由外部伪造，并重新验证登录和刷新限流。上面的 500 人压测为准备账号临时提高了额度，不能视为默认认证入口支持 500 人同时登录。
